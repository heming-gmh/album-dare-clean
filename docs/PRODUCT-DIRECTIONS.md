# 产品方向对比（v0.1 讨论稿）

状态：讨论稿，未提交。目的：在写 PRD、画原型之前，先把「这个产品到底立在哪」定下来。

## 评判标准

1. **痛点强度**：不解决会不会难受？多久难受一次？
2. **差异化**：现有产品为什么不够？我们凭什么赢？
3. **变现**：谁付钱，为什么付，付多少？
4. **冷启动**：第一次打开，60 秒内能不能看到价值？
5. **资产复用**：现有 `packages/core`（花名册 / 证据 / 闸门 / 回收站）能用多少？
6. **平台与合规风险**

---

## 方向 A：家庭相册「敢删」助手（现有方向）

**一句话**：你告诉它你在乎谁，它把一小撮照片分成三桶，只有你确认后才进回收站。

**目标用户**：30–40 岁、有孩子、手机里家庭照片上万张、存储快满但「一张都不敢删」的人。

**核心任务（JTBD）**：当手机提示空间不足时，我想安全地处理掉一批「没有家人的」照片，这样我不用逐张检查，也不会删错。

**为什么这个痛点是真的**：

- 用户不敢删的不是「照片」，是「可能重要的照片」。系统清理工具按模糊、截图、重复来分类，恰好避开了用户最怕的那一类。
- 家人的脸是用户自己定义的「重要性锚点」。这是我们和通用清理工具的根本差别。

**差异化**：

- 语义是「保护」而不是「清理」：先建花名册，再谈移出；花名册不完整就不给移出建议（现有闸门）。
- 本地人脸，不上传原片。
- 可逆：应用内回收站至少 30 天。

**变现**：订阅（¥18/月 或 ¥128/年，假设值待验证）、家庭共享包（多设备共用一份花名册，天然加价点）。

**最大风险**：

1. **冷启动最贵**：要建 3 个人 × 3 张样例才敢用。这是这个方向的头号产品问题，原型必须先回答它（例如：自动挑出「最近拍得最多的 3 个人」，让用户点确认）。
2. 系统相册在变强，各家都在做人物分类与清理建议。
3. 人脸是敏感个人信息，国内合规需要单独同意声明 + 明确的本地处理说明。

**资产复用**：`packages/core` 几乎 100%。

---

## 方向 B：存储清理 / 换机迁移

**一句话**：3 分钟找出可以安全删掉的照片视频，腾出 20G。

**目标用户**：所有存储告急的人，不分家庭；安卓中低端机更刚需。

**JTBD**：当手机提示存储不足时，我要最快知道删哪些最安全。

**差异化**：按「人物重要性」排序，而不是只按模糊、重复。清理类工具的通病是「不敢删的排前面，敢删的藏在后面」。

**变现**：工具订阅 / 买断 / 广告。市场大，单价低，获客贵。

**最大风险**：

- 同质化极强，清理类 App 口碑普遍差（诱导付费、广告），用户信任起点很低。
- 系统自带存储管理功能，会直接吃掉这个需求。
- 这类产品赢的是渠道和投放，不是产品。

**资产复用**：三桶可复用；花名册的价值被削弱，因为这类用户不会去建档。

---

## 方向 C：相册整理 / 回忆发现（不删）

**一句话**：自动把相册整理成按人、按事件的回忆流，帮你找到想看的那张。

**目标用户**：有孩子或宠物、照片多但懒得整理的人；付费意愿偏弱。

**JTBD**：当我想回看时，我要按人和事件快速找到，而不是翻 3 万张。

**差异化**：本地、不上传、花名册驱动的人物时间线。

**变现**：订阅；实体相册 / 打印是更现实的增值方向。

**最大风险**：

- 不解决「痛」，是 nice-to-have。
- 系统相册已经在做回忆、人物分类，正面撞车。
- 闸门和安全逻辑在这里完全用不上。

**资产复用**：花名册 + 人脸复用；三桶和闸门闲置。

## 横向对比

| 标准 | A 敢删 | B 清理 | C 回忆 |
| --- | --- | --- | --- |
| 痛点强度 | 强（情绪 + 决策负担） | 强（存储告急时） | 弱 |
| 差异化空间 | 高 | 低 | 中 |
| 变现能力 | 中高（订阅 + 家庭共享） | 中（量大单价低） | 低 |
| 冷启动成本 | 高（建档门槛） | 低 | 低 |
| 对现有资产的复用 | 几乎全部 | 一半 | 少 |
| 被平台收掉的风险 | 中 | 高 | 高 |

## 我的建议：选 A，但把冷启动当成第一优先级

理由：

1. 只有 A 的痛点是「情绪 + 决策负担」，不是「功能缺失」。功能缺失会被系统补上，情绪不会。
2. A 是唯一让现有 `packages/core` 全部有价值的方案，尤其是闸门——它是这个产品里最像护城河的东西。B 只用到三桶，C 用不到闸门。
3. A 的变现从「家庭」出发，天然有共享和长期订阅。
4. B 和 C 的赢家更可能是系统和平台方，而不是第三方 App。

但要修正 A 的一个隐患：**如果「建花名册」是强制的第一步，转化率会崩。** 原型要验证的核心假设是——能不能在不建档的前提下也给出可信的开始，比如先识别出照片里最常出现的 3 个人，让用户点「这是妈妈」。这一步决定了 A 是否成立。

## 如果选 A，原型要回答的 5 个问题

1. 首次打开 60 秒内，用户看到什么？（授权 → 自动发现人 → 一句话确认）
2. 「不确定」桶怎么呈现才不吓人？
3. 建议移出的理由怎么写，用户才敢点？
4. 回收站 30 天怎么让人放心？
5. 付费墙放哪里？（不能放在「敢删」的关键路径上，会毁信任）
