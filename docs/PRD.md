# album dare clean · 产品方案 v0.1

> 方向：家庭相册「敢删」助手。
> 状态：待评审。这一版的重点不是功能清单，而是**把最危险的假设挑出来，用原型去验证**。

## 1. 一句话

你告诉它你在乎谁，它把一小部分照片分三桶——「我在乎的」「不确定」「建议移出图库」。建议不会自己执行，你确认之后才进应用自己的回收站，至少 30 天可恢复。

## 2. 我们赌的三个假设

| 编号 | 假设 | 如果不成立会怎样 | 怎么验证 |
| --- | --- | --- | --- |
| H1 | 用户不敢删，是因为分不清「可能重要」和「确实没用」，不是懒 | 那这就是个伪需求，用户只是没时间整理 | 访谈 5 位目标用户 + 观察他们手动删照片的过程 |
| H2 | 家人是用户愿意投入的锚点——**但前提是零成本** | 建档门槛一高就没人用，三桶失去依据 | 原型 A/B：手动建档 vs 自动发现家人，看首次完成率 |
| H3 | 「本地处理 + 可逆」= 信任，而信任是这类产品唯一的护城河 | 用户只把它当免费清理工具，不付费 | 看回收站恢复率、付费意愿访谈 |

**这一版原型专门验证 H2。** H1 和 H3 要靠访谈。

## 3. 目标用户

- **主画像**：32–38 岁，有 1 个学龄前孩子，手机 256G 常年 90% 满。每周至少一次「想删又不敢删」，最后放弃。
- **反画像**：摄影爱好者（自己会整理）、照片很少的极简用户（不需要这个产品）。
- **不是谁**：企业用户、专业修图用户。

## 4. 核心任务

> 当手机提示空间不足时，我想安全地处理掉一批「没有家人的」照片，这样我不用逐张检查，也不会删错。

**现在的替代方案**：系统清理工具（按模糊/截图/重复，不敢删的那类排前面）、云盘（解决不了本地空间）、手动翻（放弃）。

## 5. 冷启动方案（本版最重要的设计）

**问题**：如果第一步是「建花名册：传 3 个人 × 3 张样例」，转化率会崩。

**方案：零建档启动。**

1. 首次授权后，本地先做人脸聚类（无需用户输入），得到出现频次最高的几个人。
2. 用卡片呈现：「这 3 个人在相册里出现了 1,284 次。他们是你要留住的家人吗？」
3. 用户只需点「是」，不需要上传任何样例照片——聚类结果本来就在本机。
4. 确认之后才进入「一句话整理」。没确认的人不参与判定，**也不会被误判成可移出**（安全默认）。
5. 降级路径：自动发现失败时，回退为手动选人。

**技术假设（待验证，不要写进用户可见文案）**：HarmonyOS `CoreVisionKit` 提供人脸检测与特征，但「聚类」需要自建 embedding + 聚类算法。MVP 可先用「出现频次最高的人脸」近似。这条不成立的话，H2 的验证要换方案。

## 6. 六屏信息架构

| # | 屏 | 目标 | 关键元素 | 成功信号 |
| --- | --- | --- | --- | --- |
| 1 | 权限与承诺 | 3 秒内说清「本地、不上传、可恢复」 | 三条承诺、一次性授权按钮 | 授权率 ≥ 80% |
| 2 | 发现家人 | 零成本确认 H2 | 3 张家人卡片、出现次数、一键确认 | 完成率 ≥ 70% |
| 3 | 一句话整理 | 用自然语言表达意图 | 预填句子、可改、生成按钮 | 改句率、生成率 |
| 4 | 三桶结果 | 让三桶一眼看懂，不确定不吓人 | 三色分区、关键帧、理由 | 停留时长、勾选率 |
| 5 | 确认放进回收站 | 把「建议」变成「用户决定」 | 二次确认、明确可恢复 | 确认完成率 |
| 6 | 回收站与空间回报 | 建立长期信任 | 30 天说明、恢复按钮、释放空间 | 恢复率（反向指标） |

## 7. 关键流程

**首次**：权限 → 发现家人 → 一句话 → 三桶 → 勾选 → 确认 → 回收站 → 空间回报
**日常**：打开 → 一句话（沿用上次）→ 三桶 → 勾选 → 确认
**回访**：回收站 → 恢复 / 查看剩余持有时间

## 8. 文案原则（沿用 `docs/AC.md` AC-7）

- 用「智能整理」「分组建议」「建议移出图库」。
- 不用「强力清理」，不把照片叫垃圾。
- **不承诺「释放 X GB」除非真的算过。** 宁可说「约」并给依据。
- 「不确定」永远单独呈现，不并进可删候选。

## 9. 变现与免费边界

- **免费**：完整核心流程 + 回收站。首版不收钱。
- **原则**：付费墙绝不放「敢删」的关键路径上——那会直接毁掉信任。
- **未来假设**：家庭共享花名册同步（多设备）、整理历史、纪念册/打印。
- 先把留存和「愿不愿意付」问出来，再定价。

## 10. 多端策略

- **首发**：鸿蒙。原因是原生人脸与图库能力可用，且我们已有 ArkTS 壳的骨架。
- **逻辑核心**：`packages/core` 是平台无关的 TS，可跨端复用；ArkTS 是其 TS 子集，Android/iOS 侧可通过移植或 WASM 复用。
- **UI**：三端原生还是跨平台框架，**推迟到 P2 再定**。原型不绑定技术栈。
- 原型层面三端差异只有一个：权限引导页的措辞和系统入口。

## 11. 不做清单

- 不上传原片、不做云端备份
- 不做相似图 / 最佳照片
- 不做定时或自动删除
- 不做社交分享
- 首版不做 Android / iOS

## 12. 指标

| 指标 | 说明 |
| --- | --- |
| 首次确认家人完成率 | 验证 H2 |
| 首次「放进回收站」转化 | 核心价值是否成立 |
| 回收站恢复率 | 反向指标：太高说明建议质量差、信任受损 |
| 7 日 / 30 日留存 | 是工具还是玩具 |
| 每次整理处理的条数 | 产品是否真的好用 |

## 13. 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 人脸聚类在设备端效果差 | 冷启动方案失效 | 先做技术验证；降级为手动选人 |
| 人脸属敏感个人信息 | 合规与信任 | 本地处理、单独同意、明示不出设备 |
| 系统相册做同样的事 | 被平台吃掉 | 靠「家人语义 + 可逆 + 信任」打差异 |
| 用户不愿为清理付费 | 商业模式不成立 | 首版免费，先验证留存 |
